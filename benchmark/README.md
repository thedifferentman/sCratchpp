# Scratch 内存布局性能对比

两份项目使用相同的 32 位整数数据、访问顺序、循环次数和校验公式：

- `compact-u32.sb3`：一个列表项保存一个完整整数。
- `bytes-u32.sb3`：一个列表项保存一个字节，四个连续项目按小端序保存一个整数。

全部使用原版 Scratch 3 积木，无扩展、JavaScript 扩展或 TurboWarp 专用积木。只有一个绿旗入口，所有自定义积木均设置“不刷新屏幕”。

**当前为 v2。修订版已生成并进行静态检查，未由助手运行 Scratch/TurboWarp 性能测试。**

v1 导出的结果出现大量零秒：普通“计时器”读取的是运行时缓存的时间，warp 执行期间不一定更新。v2 按以下方式计时，仍然只使用原版积木：

```text
开始天数 = 2000 年至今天数
执行测试内核
秒数 = (2000 年至今天数 - 开始天数) × 86400
```

这里先相减、再换算为秒。TurboWarp 的这个积木读取当前系统时间，不依赖同一份帧时间缓存。参考：[项目计时器实现](https://github.com/TurboWarp/scratch-vm/blob/develop/src/io/clock.js)、[daysSince2000 实现](https://github.com/TurboWarp/scratch-vm/blob/develop/src/compiler/jsexecute.js)。

已有 `bytes.txt`、`compact.txt` 属于旧版结果，原样保留。旧版零秒结果不能用于计算性能倍率；请重新加载两份更新后的 sb3 并导出新结果。新结果首行带有 `version=2,clock=dayssince2000`。

## 运行

1. 在 Scratch 或 TurboWarp 中选择“文件 → 从电脑中上传”，打开其中一份 sb3。
2. 默认参数：元素数 `50000`，每样本遍历 `200` 次，样本数 `5`，即每个样本 **1000 万次逻辑迭代**。可以使用舞台滑块修改参数；精确修改可在变量区对相应变量使用“设为”积木。
3. 点击绿旗。运行期间保持窗口在前台，关闭其他运行中的项目，保持相同的浏览器、播放器和加速模式，不拖动滑块、不显示内存列表。
4. 等待状态显示“完成：校验通过”。结果列表在测试期间自动隐藏，结束后显示；在列表上右键导出结果，或展开列表查看。
5. 使用**同样参数和设置**打开另一份 sb3，重复测试。建议交替运行 compact、bytes、bytes、compact，减少浏览器预热和温度等顺序影响。

两份项目都是独立的，结果导出后再加载另一份，避免覆盖结果。更改参数后需重新点击绿旗；一轮开始时会固定本轮参数，中途拖动滑块不会改变当前工作负载。

默认大工作量主要供 TurboWarp 测试。若在原版 Scratch 上耗时过长，可以同时降低两份项目的遍历次数。若任何实测样本不到 0.1 秒，项目会输出 `TIMING_TOO_SHORT` 并在最终状态提示增加遍历次数。每样本上限提高为 **1 亿次逻辑迭代**；N=50000 时最多遍历 2000 次。太短的样本容易受到计时分辨率和调度噪声影响；如果已达到上限仍太短，不据此得出精确倍率。

## 测试内容

| case | 每个逻辑迭代执行的工作 | 计时后的校验 |
| --- | --- | --- |
| `read` | 顺序读取一个 u32，并累加到校验和；每遍结束后对校验和取模 | 模 2³² 的读取校验和与闭式公式比较 |
| `write` | 顺序写入一个 u32，待写数值每次加一 | 解码并检查整块内存的校验和 |
| `read_modify_write` | 顺序读取一个 u32，加一，再写回 | 解码并检查整块内存的校验和 |

一个样本的逻辑迭代数 `iterations = 元素数 × 遍历次数`。`read_modify_write` 每个逻辑迭代包含一次读取和一次写入。

每项先预热最多 5 遍，再独立测试指定样本数。每个样本前重新初始化内存，初始化和正确性校验均**不计入秒数**。结果输出、样本排序和中位数计算也在计时区间之外。

计时区间包括相同的嵌套循环、指针推进，以及相应测试所需的累加或加一。内存操作在循环内直接展开，不为每次 load/store 额外调用自定义积木。两份项目的唯一内存布局差异是列表长度、地址步长和 u32 编解码。

初始化第 i 个元素（i 从 0 开始）：`270544960 + 65537 × i`。写测试从 `305419896` 开始逐次加一。数据会使用多个字节，不是只有低字节变化的小整数。所有工作负载都不发生 u32 溢出。

为支持更大的工作量，读取校验和改为每遍结束后取模 2³²，而不是把整个样本累加成一个可能超出双精度整数精度的数。期望值为 `((单遍初始和 mod 2³²) × 遍历次数) mod 2³²`。两份项目都只在**每遍结束后**执行一次取模，逐元素循环不增加此操作；所有中间校验值保持在可精确表示整数的范围内。

字节版读取采用四次列表读取与普通乘加运算。写入采用除法、floor 和 mod 拆字节，不使用位运算。最高字节可直接取商，因为工作负载保证数值属于 u32 范围。

## 读结果

列表中先是配置行，然后是 CSV 表头：

```text
layout,case,sample,iterations,seconds,checksum,expected,ok
```

`sample` 为 `1`、`2`……的行是独立样本；`median` 行是该项所有样本时间的中位数（偶数样本取中间两项的平均）。`ok=1` 表示数值校验通过。中位数行的校验和值取最后一个样本，`ok` 则汇总该项预热和全部样本是否通过。末尾还会输出 `DONE,all_checks_passed=1,timing_at_least_0.1s=1`；最后一项为 0 表示存在过短的实测样本，应增加工作量重测。

对每个 case 分别计算，**不要将不同 case 混算**：

```text
字节版耗时倍率 = 字节版 median seconds / 紧凑版 median seconds
字节版剩余速度 = 紧凑版 median seconds / 字节版 median seconds

例：compact=0.4 秒，bytes=2 秒
则耗时为 5 倍，速度为 20%。
```

建议记录表：

| 播放器及版本 | N | 遍历次数 | case | compact 中位秒数 | bytes 中位秒数 | 耗时倍率 |
| --- | --- | --- | --- | --- | --- | --- |
| | | | read | | | |
| | | | write | | | |
| | | | read_modify_write | | | |

## 边界

- 本测试测量 **u32 顺序访存内核**。数值均为非负整数，没有符号扩展、溢出检查、浮点编解码、随机访问或外部函数调用。
- 测得的是这些完整循环的耗时比，不是剥离循环成本后的单条 load/store 成本，也不是任意 LLVM 程序的总减速比。
- 两份项目使用相同的逻辑元素数，物理列表项目数分别为 N 和 4N。列表增长造成的运行时影响属于本对比的一部分。
- 最大元素数限制为 50000，以使字节版不超过原版 Scratch 的 200000 项列表添加限制。每样本总迭代数限制为 100000000，同时遍历次数不超过 100000，样本数限制为 1～9；输入参数会向下取整并限制范围，舞台会显示修正后的值。
- 两份项目计时期间只显示参数和状态；所有热循环变量、内存列表、内部计时列表和结果列表均隐藏，结束后显示结果。原版 Scratch 的 warp 仍可能让出时间片，墙钟耗时包含实际运行时调度成本。
- 浏览器 JIT、计时分辨率和系统负载会影响结果。不要把未运行的项目视为已经验证了先前估计的倍率。

## 生成与检查

`generate_benchmarks.py` 仅使用 Python 标准库。需要重建时执行：

```powershell
python .\generate_benchmarks.py
```

脚本会生成两份 sb3 及便于检查的 `*.project.json`，检查积木引用、parent/next 关系、自定义积木参数与 warp 设置、资源校验和、ZIP 完整性、旧计时器是否全部移除，以及字节拆装、扩大工作量后的整数精度和计时换算的独立算术样例。它不会启动播放器或运行项目。
