# Slot runtime regression tests

`slot_runtime_test.cpp` constructs a Scratch project using `SlotMemory` and
`SlotNumeric` directly. Its call-site assertions require one custom-block call
with one argument per slot address, so a byte-packing compatibility wrapper
cannot accidentally satisfy the direct-slot API tests. Repeated signatures must
reuse the same procedure, and every generated procedure must be warp.

The generated project checks actual bytes in both Scratch VM and compiled
TurboWarp VM. It covers same-slot and partial overlaps (including overlapping
left/right operands), persistent results across subsequent helper calls,
i1/i9/i17/i64/i65 arithmetic, 257-bit casts, shared division boundary policies,
overflow flags, non-byte stores, copies in both overlap directions, dynamic
counts, zero-length invalid-pointer accesses, and stable decoded addresses.
Constant shl/lshr/ashr helpers additionally use an independent bit-at-a-time
oracle for i1/i9/i17/i32/i64/i65/i257, byte boundaries, top-bit shifts, and the
existing deterministic overshift fallback. Each of these cases checks in-place
operation and partial overlap in both directions.
Cases execute in separate small procedures to avoid making a giant test driver
the dominant VM compilation workload.

Three additional generated projects must stop with a runtime diagnostic:
nonzero high pointer bytes, an access extending beyond memory, and an access
into the reserved code-address range. These assertions test the backend's
chosen invalid-access behavior; they do not claim that invalid LLVM accesses
have defined LLVM semantics.

```sh
cmake --build build/clang --target slot-runtime-test
build/clang/slot-runtime-test build/clang/test-output/slot-runtime
node tests/slot_runtime_vm.cjs build/clang/test-output/slot-runtime build/clang/scratch-llvm
```

On Windows, the executable names may include `.exe`. The VM runner's final
compiler argument is optional; when supplied, it additionally compiles and
executes `fixtures/slot_invalid_high_pointer.ll` as a runtime-diagnostic case.

The positive LLVM integration fixtures are part of `fixtures/manifest.json`:

- `slot_phi_recursion.ll`: three-way parallel phi cycle with fanout, recursion,
  sibling calls, constants, and live SSA values.
- `slot_memory_boundaries.ll`: overlapping memmove, dynamic zero-size operations
  with invalid pointers, legal one-past GEP, and i1/i17 masking on load.
- `slot_vector_atomic.ll`: packed i3 vector operations and dynamic extraction,
  atomic/cmpxchg old values, and a masked-off invalid pointer lane.
- `slot_constant_shift.ll`: volatile inputs with constant shifts and
  power-of-two multiplications, including negative i9 and wide i65/i257 values.

```sh
node tests/e2e.cjs --compiler build/clang/scratch-llvm --case 'slot_*.ll' --vm both
```

These four positive fixtures have also been checked using native Clang
execution as a sanity check on their expected results. Generated byte-check and runtime
diagnostic results are written to `slot-runtime-vm-report.json` next to the
generated projects. The full existing fixture suite remains necessary to test
all backend features that reuse these primitives.
